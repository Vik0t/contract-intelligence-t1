# ML-аудит — 26 октября 2026

## Что можно утверждать по результатам проверки

NuExtract3 действительно запущена локально на Apple Silicon через MLX из уже
имеющегося кеша. На синтетическом договоре поставки извлечено **11/11 контрольных
полей**, включая обе стороны/ИНН, сумму, НДС, дату и срок. Облако при этом
отключено. Это smoke test одного примера, не измерение точности на реальных договорах.

Реальные парсеры проверены на PDF, DOCX → LibreOffice → PDF и JPEG → Tesseract
rus+eng: контрольные номер, сумма и срок сохранились во всех трёх форматах.
Это чистые синтетические документы; результат не распространяется на плохие фотографии.

Суммаризация и риски проверены регрессионными тестами на маршрутизацию,
обработку всех фрагментов, отказ от внешнего вызова в local-режиме, проверку
цитат и восстановление страниц. **Реальная генерация Qwen на H100/5090 пока
не проверена:** доступа к серверу нет, аналитические веса локально не загружены.
Первичная проверка DeepCode завершалась TLS-тайм-аутом. После восстановления
доступа `/models` подтвердил точный ID `qwen3.8-flash-next`; вариант
`Qwen3.8-Flash-Next` возвращал `400 Model not found`. Клиент теперь разрешает
регистр через список моделей. Benchmark проверяет доступ до локального прогона.

Повторный реальный API-прогон после исправлений:
`tmp/deepcode-comparison-fixed.json` — три сценария × три повтора, все проверки
извлечения пройдены. Медиана warm latency API — 2,307 с против 31,2145 с в
первом локальном отчёте Mac MLX. Сводка сформирована; оба заданных риска найдены
с цитатами и страницами; отрицательный пример вернул `[]`.

Для этого исправлены ещё две несовместимости: внутреннее рассуждение Qwen
отключено через `chat_template_kwargs.enable_thinking=false`, а API-промпт
использует стандартную JSON Schema вместо специального NuExtract-шаблона.
Первичная версия поиска рисков давала ложные замечания из обычной отсылки к
законодательству и добавляла неуказанную полную предоплату. Критерии промпта
уточнены, без фильтрации конкретных контрольных фраз в коде.
Эти примеры использованы при настройке промпта и не являются независимой
test-выборкой; для вывода о качестве по-прежнему нужны отложенные договоры.

На текущих контрольных примерах итоговая точность извлечения одинакова, а API
заметно быстрее Mac MLX. Сравнение не переносится на будущую H100/5090 и не
доказывает преимущество в качестве на реальных юридических документах.

## Найдено и исправлено

| Приоритет | Недостаток | Исправление |
|---|---|---|
| P1 | Шаблон содержал нештатные типы `verbatim-string-or-null`, `YYYY-MM-DD-or-null` и др. | Используются штатные `verbatim-string`, `date`, `number`, `integer`; отсутствие значения представляется `null` самим форматом NuExtract. |
| P1 | `SUMMARY_BACKEND=local` не делал поиск рисков локальным. | Риски используют тот же локальный генератор; `RISK_BACKEND` настраивается отдельно. |
| P1 | Первые 4 000/12 000 символов выдавались за анализ документа целиком. | Сводка использует все фрагменты с последовательным объединением; риски проверяются во всех фрагментах с сохранением PAGE и удалением дублей. |
| P1 | Пустой PDF/неудачный OCR давал вход `PAGE 1`. | Документ без текстовых блоков отклоняется до запуска модели. |
| P1 | Постобработка выбирала случайную дату как окончание договора. | Дата окончания требует смыслового контекста срока; дата подписания не используется по умолчанию. |
| P1 | Верный тип договора мог заменяться типом из случайного упоминания страхования. | Валидный предсказанный класс сохраняется. |
| P1 | Разные шрифтовые фрагменты PDF читались в порядке внутренних объектов, ломая номер, стороны и условия DOCX. | Цифровой текст восстанавливается из координат слов; соседние фрагменты одного слова соединяются. Добавлен регрессионный PDF с обратным порядком объектов. |
| P1 | Произвольный JSON модели мог попасть в БД: списки вместо дат, boolean вместо суммы, выдуманные цитаты. | Добавлена типизированная схема; неподтверждённые цитатами значения очищаются, страницы уточняются по источнику. Ошибки структуры не сохраняются как результат. |
| P1 | Локальная экстракция отправляла весь длинный договор в один вызов без проверки контекста. | Разбиение на ограниченные фрагменты, объединение полей, проверка токенизированного контекста перед генерацией. |
| P1 | Одновременная ручная генерация и очередь могли конкурировать за GPU; две модели оставались в памяти. | Общая блокировка локальной генерации и последовательное освобождение моделей по умолчанию. |
| P1 | Задания после перезапуска могли остаться `running`: recovery не фиксировался в БД, свежие задания ожидали 30 минут. | Recovery фиксируется транзакцией; один процесс восстанавливает все прерванные задания и будущие отложенные retries. |
| P1 | Очередь могла заблокироваться при мгновенно завершившемся future. | Блокировка callback заменена на reentrant. |
| P2 | DOCX считался одной логической страницей, хотя просмотр показывал физические страницы. | В серверном профиле извлечение использует тот же PDF LibreOffice, что и просмотр. |
| P2 | Номер страницы риска принимался со слов модели. | Страница определяется/проверяется по дословной цитате; недоказанный номер не показывается. |
| P2 | Обрезанный по лимиту локальный ответ мог выглядеть как готовая сводка. | Незавершённая генерация возвращает ошибку; лимиты выхода вынесены в конфигурацию. |
| P2 | Старый 50-document benchmark передавал `(result, usage)` в scorer как словарь; regex ISO-даты тоже был ошибочным. | Формат возвращаемого значения и парсер даты исправлены. |

Типы и способ запуска сверены с [официальной карточкой NuExtract3](https://huggingface.co/numind/NuExtract3).
На момент проверки модель — специализированная VLM на Qwen3.5-4B, SHA
`c99dc8f5641b866aa0192b6ea78f84bf9f3535f1`. Размер модели сам по себе не
определяет качество извлечения: для замены требуется проверка нашей схемы и выборки.

## Развёртывание

`compose.yaml` — локальный профиль: CUDA 12.8 / Torch 2.7.1, NuExtract3,
Qwen3-8B, OCR, LibreOffice, PostgreSQL и Nginx. Модели скачиваются отдельной
командой, рабочая сеть backend закрыта от интернета, облачные fallback отключены.
Готовность GPU, OCR и полнота весов проверяются до старта API. Файлы весов
проверяются на наличие всех shards, но их наличие не заменяет реальную генерацию.

`compose.api.yaml` — явный дополнительный профиль DeepCode. Локальный GPU и
веса ему не нужны; образ может собираться с CPU PyTorch. Извлечение, сводка и
риски используют настраиваемые alias через `OPENAI_BASE_URL`. HF-fallback
отключён, поэтому сбой DeepCode не меняет поставщика обработки молча.

Команды и ограничения: [DEPLOYMENT.md](DEPLOYMENT.md).

Проверка упаковки на этой машине: оба Compose-профиля проходят проверку
конфигурации; Linux-зависимости разрешаются с CUDA-ограничениями; frontend-образ
реально собран. Полная сборка backend-образов и запуск на H100/5090 пока не
подтверждены. Это остаётся проверкой перед выпуском, а не выполненным GPU-тестом.

## Повторяемые проверки

```bash
# Быстрые регрессии, без весов и внешнего inference
uv run python -m pytest -q

# Настоящие PDF / DOCX / JPEG + OCR, без генерации
uv run python -m scripts.ml_check --parsing-only

# Реальные локальные модели на сервере с GPU
docker compose --env-file .env.server --profile validation run --rm ml-check

# Реальный DeepCode, только синтетический договор и отрицательный контроль рисков
docker compose --env-file .env.api -f compose.yaml -f compose.api.yaml \
  --profile validation run --rm ml-check

# Одинаковые синтетические входы, раздельные cold/warm замеры извлечения
uv run python -m scripts.benchmark_models --api-model qwen3.8-flash-next --backends local api --repeats 3 --insights
```

`ml_check` сохраняет отдельные проверки 11 полей, сводку, найденные риски,
проверку двух контрольных рискованных условий, страниц и отрицательный пример
рисков. Отчёт содержит текст только синтетического примера. Семантика сводки
пока требует ручной оценки: автоматический smoke test проверяет её непустоту,
а не доказывает фактологическую корректность.

`benchmark_models --insights` сравнивает NuExtract и API-кандидата именно по
извлечению полей, а отдельно проверяет сводку и положительный/отрицательный
контроль рисков через API-кандидата. API-ключ читается из `.env` и не сохраняется
в отчёт. Файл записывается после каждого примера, поэтому доступен и при
частичном сбое; для воспроизведения в нём сохранены только синтетические поля.

## Недостатки, которые ещё остаются

1. **Нет отложенной размеченной выборки в репозитории.** Нельзя честно сообщить
   precision/recall полей и рисков, долю галлюцинаций и качество по типам договоров.
   Нужны независимые train/dev/test группы по шаблонам и контрагентам; наличие
   похожих шаблонов в train/test завышает метрики. Старые private labels не заменены выдуманными.
2. **Валидация evidence не доказывает правильность вывода.** Настоящая цитата
   может относиться к другому полю или быть неверно истолкована. Отдельно нужны
   точность значений, соответствие цитаты, номер страницы и пропуски.
3. **Сводка при объединении может потерять или исказить факт.** Нужна человеческая
   проверка сумм, сроков, сторон, полноты и неподтверждённых утверждений на gold-наборе.
4. **Риски — предварительные замечания.** Нет валидированной юридической таксономии,
   контекста роли заказчика/поставщика и эталонной разметки юристом. Риски между
   удалёнными разделами могут быть пропущены. `[]` не означает юридическую безопасность.
5. **Сложные документы.** Таблицы, колонки, приложения с другими договорами,
   исправления, плохо читаемый цифровой слой и косые/размытые фото требуют отдельной
   выборки. Порог OCR пока опирается на длину цифрового текста, а не его достоверность.
6. **Объединение полей из фрагментов эвристическое.** Первые значения имеют
   приоритет; противоречия между разделами не показываются как отдельный конфликт.
   Перечень сторон может захватывать третьих лиц из приложений.
7. **Производительность на целевой GPU не измерена.** Нужны cold/warm latency,
   p50/p95 на длинных договорах и сканах, VRAM-пик и устойчивость потока.
   Результат Mac MLX не переносится на H100/5090. Контейнер сейчас обслуживает
   очередь одним процессом; горизонтальное масштабирование не реализовано.
8. **Воспроизводимость выпуска.** До production следует закрепить SHA обеих
   моделей и digest собранных образов, сохранить результаты benchmark. Прямые
   server-зависимости закреплены, их Linux-разрешение проверено; полная сборка
   образа дополнительно выполняет `pip check`.

Приоритет следующей итерации: получить работающий DeepCode и доступ к GPU,
прогнать одни и те же размеченные договоры на NuExtract3 и кандидате API,
затем выбирать модель по полевой точности и задержке. Решение о смене основной
модели не принимается по названию или одному удачному примеру.
