## Развёртывание

`compose.yaml` — локальный профиль: CUDA 12.8 / Torch 2.7.1, NuExtract3,
Qwen3-8B, OCR, LibreOffice, PostgreSQL и Nginx. Модели скачиваются отдельной
командой, рабочая сеть backend закрыта от интернета, облачные fallback отключены.
Готовность GPU, OCR и полнота весов проверяются до старта API. Файлы весов
проверяются на наличие всех shards, но их наличие не заменяет реальную генерацию.

`compose.api.yaml` — явный дополнительный профиль DeepCode. Локальный GPU и
веса ему не нужны; образ может собираться с CPU PyTorch. Извлечение, сводка и
риски используют настраиваемые alias через `OPENAI_BASE_URL`. HF-fallback
отключён, поэтому сбой DeepCode не меняет поставщика обработки молча.

Команды и ограничения: [DEPLOYMENT.md](DEPLOYMENT.md).

Оба Compose-профиля проходят проверку конфигурации. CPU/API-образы backend
и frontend реально собраны; запущен отдельный стенд с PostgreSQL, пройден
полный HTTP-сценарий во всех трёх форматах. Обновление схемы PostgreSQL без
reviewed_at проверено на отдельной тестовой базе. Собран также Linux/amd64
образ CUDA 12.8 с PyTorch 2.7.1+cu128; установка завершилась успешным `pip check`.
В нём под эмуляцией amd64 на Mac проверены импорт API, непривилегированный
пользователь, OCR `rus+eng`, LibreOffice и парсинг PDF/DOCX/JPG без сети.
Сборка PyTorch содержит `sm_90` (H100) и `sm_120` (RTX 5090).
Загрузка больших wheel-файлов поддерживает возобновление; кеш pip остаётся
в BuildKit и не включается в рабочий образ. Запуск генерации и измерения
производительности на H100/5090 пока не подтверждены: доступа к серверу нет.

## Повторяемые проверки

```bash
# Быстрые регрессии, без весов и внешнего inference
uv run python -m pytest -q

# Настоящие PDF / DOCX / JPEG + OCR, без генерации
uv run python -m scripts.ml_check --parsing-only

# Реальные локальные модели на сервере с GPU
docker compose --env-file .env.server --profile validation run --rm ml-check

# Реальный DeepCode, только синтетический договор и отрицательный контроль рисков
docker compose --env-file .env.api -f compose.yaml -f compose.api.yaml \
  --profile validation run --rm ml-check

# Одинаковые синтетические входы, раздельные cold/warm замеры извлечения
uv run python -m scripts.benchmark_models --api-model qwen3.8-flash-next --backends local api --repeats 3 --insights
```

`ml_check` сохраняет отдельные проверки 11 полей, сводку, найденные риски,
проверку двух контрольных рискованных условий, страниц и отрицательный пример
рисков. Отчёт содержит текст только синтетического примера. Семантика сводки
пока требует ручной оценки: автоматический smoke test проверяет её непустоту,
а не доказывает фактологическую корректность.

`benchmark_models --insights` сравнивает NuExtract и API-кандидата именно по
извлечению полей, а отдельно проверяет сводку и положительный/отрицательный
контроль рисков через API-кандидата. API-ключ читается из `.env` и не сохраняется
в отчёт. Файл записывается после каждого примера, поэтому доступен и при
частичном сбое; для воспроизведения в нём сохранены только синтетические поля.

## Недостатки, которые ещё остаются

1. **Независимая валидация эталона.** Полная разметка восстановлена: 50 договоров,
   125 форматов, 1375 проверок. Исходные метки и проверенная копия с пятью
   исправлениями версионируются отдельно. Часть цитат требует проверки пробелов,
   пунктуации и соответствия оригиналу. Корпус не является независимой от
   разработки отложенной выборкой; эталонных сводок и юридических рисков нет.
2. **Валидация evidence не доказывает правильность вывода.** Настоящая цитата
   может относиться к другому полю или быть неверно истолкована. Отдельно нужны
   точность значений, соответствие цитаты, номер страницы и пропуски.
3. **Сводка при объединении может потерять или исказить факт.** Нужна человеческая
   проверка сумм, сроков, сторон, полноты и неподтверждённых утверждений на gold-наборе.
4. **Риски — предварительные замечания.** Нет валидированной юридической таксономии,
   контекста роли заказчика/поставщика и эталонной разметки юристом. Риски между
   удалёнными разделами могут быть пропущены. `[]` не означает юридическую безопасность.
5. **Сложные документы.** Таблицы, колонки, приложения с другими договорами,
   исправления, плохо читаемый цифровой слой и косые/размытые фото требуют отдельной
   выборки. Порог OCR пока опирается на длину цифрового текста, а не его достоверность.
6. **Объединение полей из фрагментов эвристическое.** Первые значения имеют
   приоритет; противоречия между разделами не показываются как отдельный конфликт.
   Перечень сторон может захватывать третьих лиц из приложений.
7. **Производительность на целевой GPU не измерена.** Нужны cold/warm latency,
   p50/p95 на длинных договорах и сканах, VRAM-пик и устойчивость потока.
   Результат Mac MLX не переносится на H100/5090. Контейнер сейчас обслуживает
   очередь одним процессом; горизонтальное масштабирование не реализовано.
8. **Воспроизводимость выпуска.** В серверном env-шаблоне закреплены SHA обеих
   моделей; для выпуска следует сохранить digest собранных образов и результаты benchmark. Прямые
   server-зависимости закреплены, их Linux-разрешение проверено; полная сборка
   образа дополнительно выполняет `pip check`.

Следующий этап: реальный прогон контейнера на GPU НГУ и независимая экспертная
разметка сводок/рисков. Выбор между локальной NuExtract3 и API Qwen следует
обосновывать точностью на корпусе, задержкой и требованиями к размещению данных.


## Первая итерация проверки рисков с учётом стороны

В продукте используется `src/extraction/risk_review.py` и версионированный
`risk_catalog.py`: 12 редакционных правил для обычной B2B-поставки и возмездных
услуг по праву РФ. Пользователь явно задаёт вид договора и свою роль. Каталог
ещё не прошёл независимую юридическую валидацию; это не юридическое заключение.

1. Все фрагменты текста проходят сбор дословных условий, включая защитные
   положения, общий лимит, исключения, применимое право и отсылки к приложениям.
2. Все собранные цитаты сопоставляются в общем контексте с учётом нашей стороны.
   Каждое применимое правило получает решение: замечание, учтено ограничение,
   основания не найдены или требуется дополнительный контекст.
3. ID правил и цитат проверяет сервер. Заголовки, критерии, рекомендации и
   нормативные ссылки подставляются из каталога. Ссылки модели не принимаются.
   Коммерческий риск отделён от вопроса для юридической проверки.
4. Отсутствующее поле не превращается в правовой риск. При упоминании отсутствующего
   приложения модель должна запросить уточнение, а не придумывать его содержание.
5. Ошибка любого фрагмента, неверная цитата, пропуск правила или превышение общего
   контекста не дают успешного частичного отчёта. Все поля и статус оператора
   сохраняются; старые риски при новой проверке очищаются.
6. Профиль, версия каталога, SHA-256 текста, охват и результат сохраняются в БД.
   Проверка актуальности полей и ID запуска защищает от перезаписи правок и
   результатов для новой стороны. Прерванные перезапуском проверки можно повторить.

Параметры: `RISK_REVIEW_CHUNK_CHARS=10000`, `RISK_REVIEW_GLOBAL_CHARS=32000`,
`RISK_REVIEW_MAX_NEW_TOKENS=6000`. При превышении контекста источник не обрезается:
результат считается незавершённым. Успешная обработка всех фрагментов не доказывает,
что модель извлекла каждое значимое условие; OCR и полнота смысловой оценки остаются
предметом независимой проверки.

Реальный DeepCode прошёл шесть синтетических сценариев: покупатель/поставщик,
общий лимит на дальней странице, заказчик/исполнитель услуг и отрицательный пример.
Они используются при разработке и не измеряют юридические precision/recall.
Команда воспроизведения:

```bash
python -m scripts.check_risks --backend api --output tmp/risk-check.json
```

Для локальных моделей используйте `--backend local`; реальная генерация на
H100/5090 по-прежнему требует серверного прогона. Исторический `risks.py` оставлен
для воспроизводимости старого benchmark и не используется интерфейсом продукта.
Независимая разметка юристом, актуализация редакций и применимости права,
регулируемые отрасли и юридическое согласование замечаний остаются следующим этапом.


Проверка реализации каталога: **160 Python-тестов и 9 тестов фронтенда**,
production-сборка, шесть сценариев через DeepCode на хосте и в CPU/API-контейнере,
полный HTTP-сценарий PDF/DOCX/JPG. Дополнительно живой моделью проверены иностранное
право на последней странице (отказ от B2B-вывода РФ) и отсутствующее приложение с
лимитом (вопрос вместо утверждения о неограниченной неустойке). Computer use
подтвердил смену роли, скрытие старых замечаний, сохранение профиля, возврат к
фоновому запуску, раскрытие основания и выделение цитаты. Статус «Поля проверены»
относится только к данным оператора, не к юридическому одобрению договора.


## Восстановление полной разметки и исправление оценки

На Google Drive найдены исходные 50 JSON из отдельного `meta.zip`. Все 125
локальных документов побайтово совпали с исходным `dataset.zip`; внутри него
лежит устаревшая разметка только на 27 ID. Ошибка была в выборе источника при
оценке, а не в отсутствии меток у организаторов.

Загрузчик теперь использует `meta/` по умолчанию и проверяет ID, имена файлов,
структуру, даты, дубли и полноту покрытия. Неполный эталон требует явного
`--allow-unlabeled`. Установщик архива исправляет вложенность `meta/meta/`,
сохраняет существующие отличающиеся файлы и поддерживает повторное восстановление.
`rescore` переоценивает сохранённые ответы без ML/API-вызовов, отдельно фиксирует
хеши исходного inference и текущего оценщика. Замороженные результаты не изменены.
Полные метрики, различия исходных/исправленных меток и интервал неопределённости
приведены в отчёте сравнения. Разность моделей по точности на 50 договорах не
доказывает статистически устойчивого преимущества NuExtract3.
