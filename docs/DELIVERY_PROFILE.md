# Профиль поставки по ПМИ

Закреплён 28 октября 2026 года: **`pmi-rules-v1`**. Определение, проверяемое сервером и оценщиком, находится в [backend/delivery_profile.py](../backend/delivery_profile.py). Изменение обязательных настроек требует новой версии профиля. Коммит, тег и digest образов окончательного релиза фиксируются следующим этапом плана.

| Настройка | Значение |
|---|---|
| Обязательные атрибуты | Номер, дата, стороны с исходными и сопоставленными ролями, общая сумма и явно указанная валюта |
| Извлечение | `EXTRACTION_BACKEND=rules`, CPU, без загрузки модели |
| DOCX | `DOCX_USE_RENDERED_PAGES=false`: нативные абзацы, колонтитулы и таблицы; источники по логическим блокам |
| PDF | Цифровой текстовый слой, `ALLOW_OCR_UPLOADS=false`; OCR при разборе не создаётся |
| Входные форматы | PDF и DOCX; фотографии принимаются в отдельных пользовательских конфигурациях |
| Автоматическая обработка | `AUTO_EXTRACT_UPLOADS=true` |
| Внешние вызовы | `ML_ALLOW_EXTERNAL=false` |
| Дополнительные сводка и риски | `SUMMARY_BACKEND=local`, `RISK_BACKEND=local`; вызываются отдельно, не входят в оценку четырёх атрибутов |
| Хранилище поставки | PostgreSQL 16 и постоянные volumes Compose для БД и документов |
| Лимиты загрузки | 50 МБ, PDF до 200 страниц; норматив времени проверяется на договорах до 20 страниц |
| Норматив обработки | До 10 с от загрузки до получения сохранённого результата |

Сервер с `DELIVERY_PROFILE=pmi-rules-v1` отклоняет несовместимую конфигурацию при старте. `GET /runtime/profile` возвращает фактические настройки, `profile_sha256`, `rules_sha256`, `runtime_source_sha256` и версии зависимостей. Адрес БД, ключи и токены туда не входят. Эти идентификаторы профиля и исходников сохраняются в `metadata.processing` каждой обработки. SHA профиля: `5518e82918dbd40df9075893cd09029742df92f96a1e056d73b90f741003154f`.

LibreOffice используется при показе оригинала DOCX; извлечение четырёх атрибутов выполняется нативным парсером. Сводка и риски могут потребовать локальные веса по инструкции эксплуатации, их выполнение не входит в прогон оценщика. Модельные эксперименты продолжают использовать собственные конфигурации и протоколы.

## Запуск

Создайте `.env.rules` из `.env.rules.example` и задайте новый пароль PostgreSQL. Для существующей БД сохраните её действующие реквизиты.

```bash
docker compose --env-file .env.rules -f compose.yaml -f compose.rules.yaml config --quiet
docker compose --env-file .env.rules -f compose.yaml -f compose.rules.yaml build backend frontend
docker compose --env-file .env.rules -f compose.yaml -f compose.rules.yaml up -d --wait
curl --fail http://127.0.0.1:8080/api/runtime/profile
```

## Оценка через API

Используйте отдельную учётную запись испытаний. Получите её `session_token` через `/auth/login` и поместите в переменную `PMI_SESSION_TOKEN`; токен не передаётся аргументом командной строки и не попадает в отчёт. Все файлы выбранной части проверяются по хешам до первой загрузки. Путь отчёта должен быть новым.

```bash
uv run python -m scripts.evaluate_acceptance \
  --dataset tmp/acceptance-2026-10-27 --split holdout \
  --profile pmi-rules-v1 --backend rules --transport http \
  --base-url http://127.0.0.1:8080/api \
  --output tmp/pmi-http-new.json
```

Оценщик сверяет профиль сервера до загрузки, отправляет каждый PDF/DOCX, ожидает окончание очереди, читает метаданные из API, скачивает оригинал и сравнивает его SHA-256, проверяет сохранённый текст и повторное чтение метаданных. Метрики считаются по значениям из БД. Время `seconds` — от начала загрузки до первого GET с сохранённым результатом; `verification_seconds` дополнительно включает скачивание оригинала, чтение текста и повторный GET. Хеш исходников и зависимости берутся с сервера. Хеш оценщика фиксируется отдельно.

Прямой диагностический запуск `--transport direct` использует ту же функцию разбора, сервис и проверку полей, но его время не включает HTTP, очередь и БД. Для него задайте `ML_ALLOW_EXTERNAL=false SUMMARY_BACKEND=local RISK_BACKEND=local`. Только HTTP-прогон закреплённого профиля может претендовать на численные условия приёмки; ручная сверка эталонов и решение комиссии оформляются отдельно.
