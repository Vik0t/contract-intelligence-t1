# Проверка проекта по ТЗ и ПМИ

Основание: `ТЗ_Т1_2_v5.docx` и `ПМИ_Т1_2_v2.docx`. Обновлено 28 октября 2026 года. Документ фиксирует реализованные проверки и границы локальных результатов; акт приёмки подписывает комиссия на целевом стенде.

Обновление контекста по чатам и текущей рабочей копии: [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md). Оставшиеся работы и статус всех 26 критериев: [PMI_ACTION_PLAN.md](PMI_ACTION_PLAN.md). Приведённые ниже контейнерные протоколы сохраняют свою исходную версию кода; их нужно повторить на окончательном релизе.

Закреплён [профиль pmi-rules-v1](DELIVERY_PROFILE.md). Новый [протокол полного цикла через API](PMI_HTTP_2026-10-28.md) подтверждает путь nginx → API → очередь → нативный парсер → правила → PostgreSQL → GET для всех 24 файлов holdout. Он является текущим локальным доказательством четырёх атрибутов. Предыдущие замеры ниже сохранены как история.

## Генерация и оценка

```bash
uv run python -m tools.generate_acceptance_dataset \
  --output tmp/acceptance-new --count 36 --seed 20261027
ML_ALLOW_EXTERNAL=false SUMMARY_BACKEND=local RISK_BACKEND=local uv run python -m scripts.evaluate_acceptance \
  --dataset tmp/acceptance-new --split development --backend rules \
  --output tmp/acceptance-new-development.json
ML_ALLOW_EXTERNAL=false SUMMARY_BACKEND=local RISK_BACKEND=local uv run python -m scripts.evaluate_acceptance \
  --dataset tmp/acceptance-new --split holdout --backend rules \
  --output tmp/acceptance-new-holdout.json
```

Выходная директория генератора должна быть новой: существующие данные не перезаписываются. `manifest.json` содержит эталоны, принадлежность к шаблону, тип документа, разбиение и SHA-256 каждого PDF/DOCX; `manifest.sha256` фиксирует сам манифест. Оценщик проверяет хеши перед прогоном. Снимок исходного прогона находится в `tmp/acceptance-2026-10-27`; хеш манифеста: `fae9bf7b07e6664b395a264441bb974f9db5b843070ced74f713017194227f77`. Разбиение было создано до реализации `rules`.

Первый шаблон — обычный договор с шапкой и абзацами; второй — номер в колонтитуле DOCX и стороны в таблице; третий — реквизиты после отвлекающих номеров, дат, аванса, НДС и цены единицы. Третий шаблон отмечен `atypical`. В наборе есть Покупатель/Поставщик, Арендатор/Арендодатель, ИП, USD и суммы без валюты. Это ограниченные модельные формы, а не представительная выборка произвольных договоров контрагентов.

Единица оценки — договор: атрибут засчитывается только при правильном результате и в PDF, и в DOCX. «Стороны» — один атрибут, включающий обе организации, исходные роли и их сопоставление; ИНН в четыре обязательных атрибута не входит. «Сумма» включает значение и валюту, в том числе отсутствие валюты в исходнике. По умолчанию `--review-policy issued` включает сохранённые кандидаты `needs_review` в выданные значения и не скрывает ошибку из precision. Вариант `abstain` считает выданными только поля `found`; выбор политики комиссия должна закрепить до приёмочного прогона.

Оценщик считает `precision=TP/(TP+FP)`, `recall=TP/(TP+FN)`, а также долю простых договоров со всеми четырьмя правильными атрибутами. Неверный выданный ответ учитывается как FP и как пропуск правильного эталонного значения FN. Сохраняются числа TP/FP/FN, ошибки, время, результаты по шаблонам и отдельно нетиповые формы. Нулевой знаменатель precision даёт `null`, а не 100 %. Ошибки обработки не исключаются из знаменателя.

Начиная с `pmi-four-attributes-v2`, наличие атрибута в эталоне фиксируется отдельно (`expected_present`). Корректное отсутствие значения не увеличивает TP, FP или FN; выданное значение при пустом эталоне даёт только FP. При правильном ответе в одном формате и пропуске в другом договор получает FN без ложного FP. Корректное отсутствие считается правильным результатом поля при оценке документа; сбой обработки не может дать успешный документ. Новый JSON содержит `scoring_version` и `scoring_sha256`; старые отчёты не перезаписываются.

Все четыре атрибута совпали у 8 из 8 простых договоров. Для 4 нетиповых договоров precision и recall по каждому атрибуту также составили 100 %. Проверены 24 файла (12 договоров × 2 формата), ошибок обработки нет. В первом прогоне максимальное время парсинга и извлечения одного файла составило 0,0177 с; окончательный протокол с хешем правил и фактическими временами сохраняется в `tmp/acceptance-2026-10-27-holdout-final.json`.

После исправления оценщика результат подтверждён заново: `tmp/pmi-fixes-2026-10-27/rules-v2-snapshot.json`, максимум 0,0084 с, те же 12 договоров и 100 % четырёх атрибутов. Протокол относится к сохранённому снимку исходников с хешем правил `1357ea32cd2944ad8af70922a7dddf23bbeb08bf16f8c8bb9c2b8d6f86399202`. Манифест и эталоны не изменялись; промежуточный `rules-v2-holdout-final.json` также сохранён.

28 октября тот же результат подтверждён через HTTP на закреплённом профиле с PostgreSQL: `tmp/pmi-profile-2026-10-28/http-holdout-final.json`. Максимум полного цикла от загрузки до сохранённого результата — 0,174 с, ошибок нет. Проверены оригиналы, сохранённый текст, повторное чтение и соответствие БД. Прямой прогон того же снимка дал идентичные метрики. Инструкция HTTP-запуска — в [паспорте профиля](DELIVERY_PROFILE.md), версии и хеши — в [протоколе](PMI_HTTP_2026-10-28.md).

Эталоны имеют статус `pending_manual_review`. Оценщик поэтому сохраняет `formal_acceptance_ready=false`, даже при достигнутых численных порогах. Для подтверждения по ПМИ нужны ручная сверка эталонов, утверждение политики подсчёта, запуск передаваемой версии на НГУ и решение комиссии. Результат rules-профиля не переносится на NuExtract3, Qwen, исходный корпус из 50 договоров или реальные документы. Пересчёт старого корпуса описан отдельно в [результатах сравнения моделей](../evals/RESULTS_2026-10-27.md).

## Проверка перед поставкой

Текущая проверка 28 октября: 320 тестов Python и 10 frontend прошли, CPU backend и frontend/nginx собраны и запущены с PostgreSQL. Все результаты относятся к `tmp/pmi-profile-2026-10-28/runtime-final/`; после объединения параллельных изменений требуется проверка окончательного релиза. Проверки прежних снимков ниже сохраняются отдельно.

После исправлений оценщика и метаданных итоговый прогон сохранённого снимка дал 304 пройденных теста Python; журнал `tmp/pmi-fixes-2026-10-27/pytest-snapshot-complete.log`. Состав 102 файлов и хеши — `runtime-snapshot.json`, исходники — `verified-runtime/` в той же директории. Тесты и оценка относятся к этому снимку, пока другие чаты продолжают менять общий каталог. Также прошли 10 тестов frontend и production-сборка. Настоящий MLX-загрузчик офлайн загрузил `numind/NuExtract3-mlx-8bits` с ревизией `bd8048c41019a63cdcbba93aa2dbfde06cbfc490`; генерация не запускалась. API-тест проверяет запись модели в БД без подстановки локальной ревизии. Для провайдера, не сообщающего ревизию, сохраняется `null` и `model_revision_source=unknown`.

Ранее в контейнерном стенде с PostgreSQL проверены пакет 3 корректных + 1 повреждённый файл, хеши оригиналов, заполнение четырёх атрибутов, повторная обработка с прежним ID метаданных, запрет чужого чтения/удаления и удаление собственного документа. В отдельном PDF на 20 страниц сумма правильно найдена на странице 20; парсинг и правила заняли 0,0082 с на Mac. При реальной остановке тестового PostgreSQL API вернул 503 с русским пояснением и восстановился после запуска БД. Сопоставление цитаты с отрендеренным DOCX исправлено для слов, разделённых на кириллические и латинские шрифтовые фрагменты. Это исторический контейнерный протокол; текущий релиз нужно собрать и проверить отдельно.
